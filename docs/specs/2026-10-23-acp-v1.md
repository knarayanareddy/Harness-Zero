# Official ACP v1 adapter

**Status:** offline SDK vertical slice locally integrated/verified; editor and
global/artifact qualification remain open; not shipped.  
**Owner:** parent integration owner. **Task:** T20. **Date:** 2026-10-23.

## Problem and evidence

The real official Python client `agent-client-protocol==0.12.1`, generated against
`refs/tags/schema-v1.19.0`, sends integer protocolVersion1. The current parent
returns legacy string0.1; the client receives that real response and rejects it
with a typed validation error. The exact wheel hash, wire capture, command,
exception and clean subprocess exit are retained in the ignored T20 SDK probe.
This proves a compatibility failure, not an interoperability pass.

## Approach and non-goals

Use one protocol adapter over the existing Commands, gate, session ownership and
bounded stdio lifecycle. Keep the SDK a pinned development/test dependency, not a
production import or a second runtime. No new workspace authority, provider,
store, implicit file/resource fetch, terminal or client-supplied MCP connection.
See ADR0003 for the temporary legacy compatibility decision.

## Thin slices

1. Negotiation and sessions: actual SDK initialize, create/list and boundary cases.
   This is an isolated intermediate candidate only. Do not integrate or advertise
   official compatibility while required turn operations are unimplemented.
2. Turns and interactions: typed content/update mapping, correlated permission
   requests, cancellation completion ordering and EOF cleanup. Integrate only
   after the complete offline vertical slice is independently reviewed and tested.

The second slice is implemented in two reviewable steps on the isolated branch:
text/resource_link prompts, real updates and cancellation first; bidirectional
permissions and approval-only receiver activation second. Neither intermediate
step is integrated or advertised as complete compatibility. A phase-one test that
expects an unimplemented prompt method may evolve to an explicit invalid-session
or invalid-content denial once that method exists, retaining zero model/tool
effects and dialect-lock assertions. Original R05 and all legacy assertions stay
unchanged.

## Slice-one acceptance

- [x] The real SDK accepts integer-version initialization from an actual stdio
  subprocess, replacing the existing observed validation failure.
- [x] Valid integer version negotiation returns the supported integer version;
  malformed explicit version types cannot silently select legacy mode.
- [x] Once a connection selects v1 or legacy, it cannot downgrade, upgrade or mix
  dialects. Missing-version legacy initialize remains an explicit compatibility
  exception, not an official v1 validation claim.
- [x] Actual SDK new_session/list_sessions calls use canonical Commands and typed
  response shapes; only this connection's sessions are returned.
- [x] Client cwd must be absolute and resolve to the launched workspace. Reject
  alternate workspace roots, nonempty MCP server lists and unsupported additional
  directories before session creation or other effects.
- [x] Official-intent session operations before initialization fail closed. The
  unchanged original R05 no-initialize legacy session/new request still passes.
- [x] Existing32 ACP controls and strict response/cleanup deadlines remain intact.
  The incomplete v1 turn path must not fabricate completion or tool execution.
- [x] New tests require the pinned SDK through the dev dependency. No silent
  import-skip or a self-matching JSON fake substitutes for official-client proof.

Verification uses a worker-owned Python3.11/3.12 environment with real dependencies,
source-import checks, the actual SDK subprocess client and existing legacy tests.
Keep parent/shared environments read-only. Small new seam checks may run during
browser work; the parent serializes broader matrices, builds and stress tests.

## Later acceptance and open items

The second slice must cover text and baseline resource_link without dereferencing
resources; real update variants; bounded typed permission correlation; approve,
reject, late-response, foreign-session and cancel/EOF negatives; and cancelled
prompt responses only after owned work and prior updates finish. Advertise no
unsupported image/audio, elicitation, terminal/fs, MCP, authentication or replay.

Before enabling v1 permission UI, prove unsupported structured questions remain
headless. At planning time the InteractionBroker eligibility helper accepts a kind
but checks only session-level interactive presence. The separate availability
prerequisite now fixes this with trusted kind metadata, not frame-filter inference.
An integrated permission-only receiver must not make
ask_user wait for a question UI it does not provide. If a separate typed-client
eligibility prerequisite is needed, capture its own narrow scope and fail-first
controls, preserving legacy approval/question consumers. Do not bypass the gate,
auto-approve, invent an answer or conflate questions with permission options.

The completed offline source is independently reviewed, a quiet-window77-case
SDK/legacy/broker group passes per version, and the integrated parent's414-case
bridge/UI/broker/privacy/session/checkpoint/resource groups pass on3.11/3.12.

### Permission expiry follow-up

The first permission candidate is not accepted. Source review finds that its
adapter starts a fresh timeout when forwarding begins and the shared broker can
claim an approval without checking expiry. The correction has this contract:

- Set an internal monotonic approval deadline when the broker creates the
  request, before persistence/publication; those operations consume the budget.
  This is ephemeral request state, not a new serialized SDK field or permission.
- Check expiry when receiving the ACP response and when the shared broker claims
  a resolution under its existing resolution lock. Delayed forwarding, a queued
  resolver or a delayed timeout callback must not extend approval eligibility.
- Once a timely resolution is claimed, retain the existing durable-record-before-
  acknowledgement behavior. Expired unclaimed work is settled by the existing
  timeout path; do not invent a user approval or cancellation.
- Preserve original operation/cancellation limits. Add deterministic controls for
  expiry before forwarding, after response receipt but before resolution claim,
  and before the timeout callback settles, plus timely positive controls.
- Consolidate all nine permission controls into the default-discovered
  `tests/plugins/bridges/test_acp_interop.py`; preserve their assertions and the
  rejected five-file candidate. The conflicting dispatch shorthand is a process
  error, not authorization to omit these controls from the default gate.

The explicitly expanded repair scope is the existing four protocol slice files
plus `harness/kernel/interactions.py` and a new default-discovered
`tests/kernel/test_approval_deadlines.py`. Parent integration must recheck the
shared broker destination and refresh affected UI/CLI/broker/bridge controls.
The existing temporary `newtest_acp_interop.py` may be removed only after its
bytes are preserved and all controls are consolidated without loss.

An actual supported editor journey is a separate required tier. Zed was not found
in the two checked application locations; no installation, launch or integration
was performed. SDK success alone does not close T20 or establish general IDE support.
