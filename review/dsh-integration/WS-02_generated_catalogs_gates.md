## 1. Outcome

`harness catalog` is a CLI group that **generates** the reference docs from the running registry and **checks** them in CI:

```
harness catalog gen            # rewrites docs/catalog/*.md + docs/events.schema.json + docs/catalog/ui.json
harness catalog --check        # exit 1 on any drift, missing README section, undeclared setting, unknown doc ref, uncovered tool
harness catalog readme <plugin>   # prints the Configuration table for a plugin README
```

Generated files carry a header `<!-- GENERATED by `harness catalog gen` — do not edit -->`. CI fails if the tree differs after `gen`, exactly like the existing events-schema step. The hand-written `docs/PLUGIN_CATALOG.md` is replaced by the generated one (and it stops claiming numbers it cannot prove).

## 2. Current state (verified)

- `docs/PLUGIN_CATALOG.md` is prose; nothing checks that the 35 plugins it lists are the 35 in the tree, nor their capabilities or settings.
- Settings: `commands.settings_schema` hand-codes 11 properties; `SettingsStore.register_schema()` exists but no plugin manifest sets `[settings] schema=`. Settings used by plugins (`plugins.bridge-mcp-client.servers`, checkpoint settings, …) are undocumented and unvalidated.
- Events: `docs/events.schema.json` is generated and gated (good); there is no producer/consumer map — the web client handles 19 of 30 types (review v0.2.1 §3), nothing says which 11 are intentionally unrendered.
- UI: `tests/frontends/test_static_contract.py` checks IDs referenced by `app.js` exist in `index.html` and bans inline handlers/alert — a useful base, but there is no check that a `data-command`/button maps to a registered command (the review found 10 `data-notice` and 9 `noop` bindings).
- Scaffold supports only `--kind context`.
- Import boundaries are tested kernel→plugins and plugins→sdk-only (`test_plugins_import_only_sdk`), already satisfying half of P6.

## 3. Design

### 3.1 Catalog model (`harness/kernel/catalog.py`, kernel-side, read-only)

```python
@dataclass(frozen=True)
class Catalog:
    plugins: list[PluginEntry]      # name, version, family, provides, capabilities, settings namespace, readme ok?, conformance kit
    tools: list[ToolEntry]          # name, plugin, risk_class, timeout_s, input_schema summary, hints, description first line
    settings: list[SettingEntry]    # key, owner (kernel|plugin name), type, default, group, widget, source file
    events: list[EventEntry]        # type, durable, producers (module:line), payload schema ref, renderer (client module) or "none (live)"
    commands: list[CommandEntry]    # name, handler, args schema (from signature/type hints), emits
    ui: UiContract                  # data-command / data-event / data-setting attributes found in static client (parsed, not executed)
    scenarios: list[ScenarioEntry]  # from tests/scenarios/*/scenario.yaml: tools, commands, events covered
```

Built by `build_catalog(workspace, config_dir)` which runs `bootstrap_kernel` hermetically (temp HOME, mock provider) so **the catalog is what the registry actually loaded**, not a static parse. Producers of events are found by a static grep for `emit("<type>"` / `HookEvent.<X>` (good enough; listed as `heuristic` in the output header).

### 3.2 Generated outputs

```
docs/catalog/
├── PLUGINS.md        # table per family; per-plugin: provides, capabilities, settings keys, README status, tests
├── TOOLS.md          # one table; + per-tool section with description + input schema (collapsed)
├── SETTINGS.md       # grouped as the UI groups them; owner column
├── EVENTS.md         # type | durable | producers | client renderer | scenarios covering it
├── COMMANDS.md
├── UI_CONTRACT.md    # every interactive element: selector → command/setting; orphans section must be empty
└── catalog.json      # machine-readable union (consumed by the UI contract test in WS-05 and by tests/scenarios coverage)
docs/events.schema.json   # unchanged location, now produced by `catalog gen` too
```

### 3.3 Checks (`harness catalog --check [section]`)

| check | fails when |
|---|---|
| `drift` | `gen` output ≠ tree |
| `readmes` | a plugin lacks `README.md` or any of the 5 sections in `templates/PLUGIN_TEMPLATE.md`; Configuration table ≠ `catalog readme <plugin>` output |
| `settings` | a `settings.get("…")` / `ctx.settings.get("…")` literal in `harness/**` names a key not declared in `KERNEL_SCHEMA` or any plugin `settings.schema.json`; or a schema key is never read (dead setting) |
| `refs` | a backticked identifier in `README.md`, `docs/*.md`, `CHANGELOG.md` that *looks like* a tool/command/setting/plugin/route (`[a-z_]+\.[a-z_.]+`, `harness [a-z]+`, `/[a-z]+(/[a-z_]+)*`) is not in the catalog (allow-list file `docs/catalog/refs.allow`) |
| `ui` | an interactive element without a registered command; a `durable` event without a renderer; a renderer for an unknown event (WS-05 implements renderer registry; until then the check runs in `warn` mode and prints the orphan list) |
| `scenarios` | a tool or command not referenced by any `tests/scenarios/*/scenario.yaml` (`warn` until WS-01 has landed; then `fail`) |
| `boundaries` | plugin→plugin import (extends `test_import_boundaries.py`) |

Exit code 1 with a per-check summary; `--format json` for tooling.

### 3.4 Scaffold kinds

Extend `KIND_TEMPLATES` with `tool`, `policy`, `hook`, `store` producing exactly the layout in `templates/PLUGIN_TEMPLATE.md` (manifest, `plugin.py`, `<kind>.py`, `README.md` with the 5 sections pre-filled with TODO markers that `catalog --check readmes` rejects until replaced, `settings.schema.json` when `--with-settings`, `tests/test_conformance.py` using the matching kit).

### 3.5 Settings ownership migration (P6, mechanical part)

For each built-in plugin that reads settings today, add `settings.schema.json` + `[settings] schema=` in its manifest and have the registry call `SettingsStore.register_schema("plugins.<name>", schema)` at load. The hand-coded dict in `commands.settings_schema` is reduced to the aggregation (WS-05 replaces the *rendering*; WS-02 only makes the data source truthful):

```python
async def settings_schema(self) -> dict[str, Any]:
    registered = self.settings.get_registered_schemas()      # {"kernel": {...}, "plugins.<name>": {...}, "secrets": {...}}
    props: dict[str, Any] = {}
    for ns, schema in registered.items():
        for key, prop in schema.get("properties", {}).items():
            props[f"{ns}.{key}"] = prop
    groups = sorted({p.get("x-ui", {}).get("group", "Other") for p in props.values()}, key=GROUP_ORDER.index)
    return {"groups": groups, "properties": props}
```

The secrets block becomes a `secrets` namespace schema contributed by the provider plugins that need them (`providers/openai_compat` declares `OPENAI_API_KEY`, etc.).

### Skeleton: `harness/cli_catalog.py`

```python
@click.group(name="catalog", invoke_without_command=True)
@click.option("--check", "check", is_flag=True, help="Verify generated docs, READMEs, settings, refs, ui, scenarios")
@click.option("--section", multiple=True, type=click.Choice(["drift","readmes","settings","refs","ui","scenarios","boundaries"]))
@click.option("--format", "fmt", type=click.Choice(["text","json"]), default="text")
@click.option("--workspace", "-w", default=".")
@click.pass_context
def catalog(ctx, check, section, fmt, workspace):
    if ctx.invoked_subcommand: return
    if not check: raise click.UsageError("use `harness catalog gen`, `harness catalog --check` or `harness catalog readme <plugin>`")
    report = asyncio.run(run_checks(Path(workspace), sections=section or ALL_CHECKS))
    click.echo(report.render(fmt)); ctx.exit(0 if report.ok else 1)

@catalog.command("gen")
def gen(...): cat = asyncio.run(build_catalog(...)); write_outputs(cat, Path("docs/catalog")); write_events_schema(cat, Path("docs/events.schema.json"))

@catalog.command("readme")
@click.argument("plugin")
def readme(plugin): click.echo(render_config_table(asyncio.run(build_catalog(...)).plugin(plugin)))
```

## 7. Non-goals / cautions

- Do not build a docs website; markdown + JSON in-tree is the deliverable.
- The event-producer scan is heuristic; declare it so in the header and keep the regexes in one place.
- Do not "fix" undeclared settings by deleting the reads — declare them with the real defaults, after reading the code that uses them.
- `refs.allow` is for prose that intentionally names things outside the tree (e.g. `pip install`); every entry needs a comment.
- Keep `docs/events.schema.json` path and format stable — the client and WS-01 goldens depend on it.
